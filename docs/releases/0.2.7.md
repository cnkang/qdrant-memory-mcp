# MCP distribution 0.2.7

MCP distribution 0.2.7 selects the published Runtime 0.5.3 release. Runtime
0.5.3 fixes the Hermes Qdrant Memory Provider lifecycle after initialization
fails, including WriterLease contention. This metadata-only MCP package still
delegates its implementation to the Runtime.

## Changes

- Pin `hermes-plugin-qdrant-memory[mcp]==0.5.3`.
- Update MCP Registry metadata and exact installation examples to 0.2.7.
- Keep the four MCP tools, their schemas, stdio transport, scope rules and stored
  data unchanged. No migration or collection schema change is required.
- Keep the managed WorkBuddy/DSH launcher and DSH bundle versions unchanged:
  they use the standalone MCP entrypoint and do not instantiate Hermes' native
  MemoryProvider, so this provider lifecycle fix does not require an npm release.

## Upgrade

Update the exact package pin and restart the MCP client so it creates an
environment with Runtime 0.5.3. Existing profiles and memory data remain in
place. Hermes Native Provider users should update the Runtime pin and restart
Hermes/Gateway to load the lifecycle fix; recovery remains explicit after the
competing writer exits, with no background retry loop.

```sh
uvx --from 'qdrant-memory-mcp==0.2.7' qdrant-memory-mcp --help
```

## Verification and limits

- The release workflow builds and tests the wheel and sdist against public
  Runtime 0.5.3 before PyPI publication.
- After PyPI publication, install the exact MCP version in a clean environment,
  check `tools/list`, and perform an isolated explicit write/read.
- Runtime 0.5.3 lifecycle evidence and remaining environment limits are recorded
  in the [Runtime validation record](https://github.com/cnkang/hermes-plugin-qdrant-memory/blob/main/docs/validation.md).
- Update Registry version `io.github.cnkang/qdrant-memory` to 0.2.7 only after
  the PyPI package is public and public-install acceptance passes.
